# Maintainer Runbook

This is the single control-plane document for operating this private stack.

Use this file first when the runtime is unhealthy.
Use [runtime/SUPERVISOR_COMPLETION_LOOP_RUNBOOK.md](runtime/SUPERVISOR_COMPLETION_LOOP_RUNBOOK.md) only for the strict supervised-completion loop after the broader runtime is already understood.
For the hermes Python control plane (lane routing, proxy, bench), see [hermes/README.md](hermes/README.md) — it is operated independently of the surfaces below.

## Control Plane

- Stack config: `runtime/config.json`
- Platform registry: `runtime/platforms.json`
- Setup entrypoints: `setup-opencode.sh`, `setup-vscode.sh`
- MCP server and tests: `mcp-server/`
- VS Code agent mirrors: `adapters/agents/` (generated by `scripts/sync-vscode-agents.mjs`)
- Hermes control plane: `hermes/` (`scripts/hermes_orchestrator.py`, `config/orchestration.json`)

## Fast Verification

Run these before chasing deeper failure modes:

```bash
bash -n setup-opencode.sh
bash -n setup-vscode.sh
npm --prefix mcp-server test
npm --prefix mcp-server run design-pack:verify-layout
npm --prefix mcp-server run harness:ci
node scripts/sync-vscode-agents.mjs --check
(cd hermes && python3 -m unittest discover -s tests)
```

If one of these fails, fix that surface before assuming the router or supervisor is wrong.

The layout, agent-sync, lint, and test checks also run automatically in CI (`.github/workflows/ci.yml`) on every push and pull request.

## Failure Modes

### Host Unreachable

Symptoms:

- remote Tailscale hosts stop receiving delegated work
- routing falls back to local unexpectedly
- health checks show a lane as unreachable

Checks:

```bash
tailscale status | grep skippy
curl -s http://skippy-debian-5090:30000/v1/models
rg -n '"enabled"|"endpoint"|"provider"' runtime/platforms.json
python3 hermes/scripts/hermes_orchestrator.py health
```

Recovery:

1. Confirm the affected host still exists in `runtime/platforms.json` and is enabled.
2. Confirm the host endpoint and network scope still match the real Tailscale lane (and `hermes/config/orchestration.json` for the hermes lanes).
3. For the Skippy Ollama lane, verify `OLLAMA_HOST` is still bound to the tailnet on the rig (see `hermes/README.md`).
4. Re-run `npm --prefix mcp-server test` after registry changes so routing assumptions are checked against the updated registry.

### Model Mismatch

Symptoms:

- an agent selects a provider/model pair that is no longer present on the chosen host
- a task routes correctly but fails on model availability

Checks:

```bash
rg -n 'model' runtime/config.json runtime/platforms.json runtime/model-recommendations.json
python3 hermes/scripts/hermes_orchestrator.py inventory --probe-tool-calls
```

Recovery:

1. Treat `runtime/platforms.json` as the shipped registry and keep it aligned with what the lanes actually serve (`ollama list`, `curl .../v1/models`).
2. If the desired remote model is gone, let routing fall back to the next lane instead of pinning the stale model back in.
3. Keep `runtime/model-recommendations.json` aligned with the registry after model changes.

### Unexpected Remote Routing

Symptoms:

- coding work leaves the expected lane without a clear reason
- controller agents stop preferring the primary lane
- delegated work lands on the wrong tier

Checks:

```bash
npm --prefix mcp-server test
npm --prefix mcp-server run harness:ci
```

Recovery:

1. Verify that the registry still marks the intended lane enabled and its tier order is intact (`selectionPolicy.defaultOrder`).
2. Verify cloud escalation is still gated (`selectionPolicy.cloudEscalation.optIn` false unless deliberately enabled).
3. Inspect `mcp-server/src/index.ts` routing sections before changing registry values in isolation.

### Watchdog Or Recovery Loops

Symptoms:

- sessions bounce between `running`, `cooldown`, and recovery without converging
- completion attempts fail with stale evidence or missing judge output
- continuation prompts repeat without new work landing

Checks:

```bash
npm --prefix mcp-server test
npm --prefix mcp-server run harness:ci
```

Recovery:

1. Follow the strict completion sequence in [runtime/SUPERVISOR_COMPLETION_LOOP_RUNBOOK.md](runtime/SUPERVISOR_COMPLETION_LOOP_RUNBOOK.md).
2. Reproduce the failure with deterministic verification before changing reliability thresholds.
3. Treat stale evidence, memory drift, and judge failures as blocking signals, not noise.
4. Only tune watchdog thresholds after the regression suite is green.

## Change Discipline

When a fix touches routing or reliability behavior:

1. Patch the smallest owning surface.
2. Add or update deterministic regression coverage in `mcp-server/src/reliability.test.ts` when the failure mode is policy- or recovery-related.
3. Re-run the full validation baseline before calling the cleanup complete again.

Agent metadata (model, temperature, steps, permissions, descriptions) is canonical in
`runtime/config.json`. The `runtime/agents/*.md` files carry prompt content, and
`adapters/agents/*.agent.md` are generated VS Code mirrors; when you change an agent,
update `runtime/config.json` and `runtime/agents/` first, then regenerate mirrors with
`node scripts/sync-vscode-agents.mjs`.
